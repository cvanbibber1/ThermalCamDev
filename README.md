# ThermalCamDev

Firmware and host tooling for a radiometric thermal camera built around an
**STM32F412CGU6** and a **Teledyne FLIR Lepton 3.1R**. Every pixel is an
absolute temperature. The camera presents itself over USB as a UVC video device
plus a CDC control port, and over RS-422 as a slave on a DICE/STP flight bus.

This README is the developer's entry point. If you only want to *use* the
camera, read the [User Guide](USER_GUIDE.md) instead.

## Quick start

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\pio.exe run -e target
```

Artifacts land in `.pio/build/target/` as `firmware.elf` and `firmware.bin`.

Run the window against a camera on USB, or on the flight link:

```powershell
python .\tools\thermalcam_app.py
python .\tools\thermalcam_app.py --source rs422 --rs422-port COM34
```

## How the firmware is put together

A bare-metal event loop over STM32Cube HAL. No RTOS and no dynamic allocation:
every buffer is static, so the memory ceiling is known at link time.

```
src/main.c              the loop: capture, dosimeter, USB, link, settings
src/board/              clocks, pins, DMA, and the HAL interrupt vectors
src/lepton/             sensor bring-up, VoSPI capture, frame assembly, FFC policy
src/protocol/           packet formats, the image codec, command dispatch
src/drivers/            the RS-422 STP link, and the development COBS transport
src/usb/                UVC video and CDC control
src/settings.c          flash-backed configuration
src/health.c            the counter block reported in telemetry
include/app_config.h    every tunable in one place -- start here
```

`include/app_config.h` is the file to read first. Frame geometry, the shutter
policy, the dosimeter transfer function, the RS-422 baud and node address, and
every codec parameter are there with the reasoning attached.

The loop runs each task to completion and never blocks. Anything that would
block is either a state machine driven by `HAL_GetTick()` or split across
calls -- see the encoder below, and `settings_task()`, which defers a flash
sector erase because it stalls the core for over a second.

## The capture path

The Lepton streams **VoSPI**: 164-byte packets, 60 to a segment, 4 segments to
a frame, each packet carrying its own CRC. Packets may be discard packets, and
recovering from lost sync requires holding chip-select idle for more than
185 ms.

The transport is a **circular SPI DMA** with half- and full-transfer handover.
The alternative, restarting a transfer per chunk, left 23% gaps in the clock
and the sensor lost sync. Two chunk buffers of 19,680 bytes each mean the
**DMA must be serviced every 12.6 ms** -- a deadline that shapes everything
else in the firmware, the codec especially.

Two hardware quirks are handled in `lepton_capture.c`:

- **SPI2 samples one bit late** on this board, so `detect_bit_phase()` derives
  the shift from the data itself rather than assuming alignment.
- **The FFC shutter-mode object (CID 0x023C) must never be written.** Writing
  it corrupts the object and silently disables automatic correction. The
  firmware only ever reads it, and issues `RUN FFC` on its own schedule.

Frames are double-buffered in `vospi_parser_t`. A reader can pin the published
frame with `lepton_capture_hold_frame()` while it drains one; the UVC path
deliberately does not, because pinning collapsed its rate from 8.8 to 0.11
frames a second. The note in `usb_video_if.c` explains why reading it unpinned
is safe.

## Image compression

`src/protocol/frame_codec.c`, mirrored on the host by `tools/frame_codec.py`.
The two must agree exactly; read them together if you change either.

**It is lossless.** Every pixel out of the decoder is bit-identical to what the
sensor produced.

Each frame is predicted with the **median-edge predictor from JPEG-LS**, run
either over the frame itself (a keyframe) or over its difference against the
previous frame. Residuals are zigzag folded and **Rice coded**, with one
parameter per block of 32 pixels chosen by the classic mean estimator.

Measured over 50 frames of real footage:

| Scheme | Ratio |
|---|---:|
| Keyframe, spatial only | 2.4x |
| Difference frame | 3.9x |
| zlib -9, for reference | 1.75x |
| lzma, for reference | 2.16x |

A purpose-built predictor beats a general compressor here because it knows the
data is a two-dimensional field of correlated 16-bit samples.

### Two constraints that shaped it more than the ratio did

**The encoder cannot block.** A frame costs about 16 ms against that 12.6 ms
DMA deadline. Encoding in one call dropped the sensor into resync and cost a
third of the capture rate. `frame_codec_encode_step()` is therefore resumable,
a band of rows at a time, and the link layer runs it under a time budget
(`APP_CODEC_STEP_BUDGET_US`). This file is also built `-O3` by pragma: the
project default of `-Os` leaves the per-pixel helpers un-inlined and the same
frame takes 56 ms.

**The encoder cannot lag the link.** Waiting for a whole frame before sending
its first chunk serialised encoding and transmission. Chunks go out as the
encoder produces them, which is why the **checksum is a trailer, not a header**
-- there is nothing to write at the front once the opening chunk has gone. Two
output slots let the encoder start the next frame while the current one drains.

### Guarantees worth knowing

Each encoded frame ends with an **FNV-1a checksum of the source pixels**, so
the ground side proves losslessness on live traffic rather than assuming it.

The checksum and the reference copy are both built from the *same reads* as the
encode. That is what makes it safe to encode from the live published frame
without pinning it: if the parser ever did overtake the encoder, the frame
would still decode and verify, and the worst artifact is a seam.

A difference frame is undecodable without its predecessor, so the camera sends
a keyframe every `APP_CODEC_GOP` frames -- currently 12, about two seconds --
bounding what one lost packet can spoil. If a frame will not fit
`APP_CODEC_BUFFER_BYTES`, the encoder declines and the link layer sends the raw
frame instead, degrading to the uncompressed rate rather than failing.

## The RS-422 wire format

USART2 through an ADM2582E, 921600 8N1, as an STP/DICE slave.

| Setting | Value |
|---|---|
| Sync word | `0x1ACFFC1D`, on the wire as `1A CF FC 1D` |
| Byte order | Big endian, every multi-byte field |
| Checksum | CRC-16/CCITT-FALSE: poly `0x1021`, seed `0xFFFF`, no reflection, no final xor |
| Checksum position | The last two bytes of every packet, both directions |
| Checksum coverage | Everything after the four sync bytes, up to but excluding the checksum |
| This camera's Target ID | `0xC7` |

| Type | Direction | Size | Meaning |
|---|---|---:|---|
| `0x10` | in | 120 | Command; answered with an 8-byte ACK |
| `0x81` | in | 14 | Vitals request; answered with 1256 bytes |
| `0x85` | in | 14 | Stop the image stream |
| `0x86` | in | 14 | Stop the image stream, with loss |
| `0x87` | in | 14 | Start the image stream; data packets are 1288 bytes |

Transmitted data reuses the request type codes; direction and size distinguish
them, as the specification warns. Definitions live in
`include/protocol/stp_protocol.h` and `include/stp_link.h`.

### The vitals payload

1248 bytes, after the 6-byte header and before the 2-byte checksum. All
multi-byte fields are big endian.

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | Layout version, currently 1 |
| 4 | 4 | Camera uptime, milliseconds |
| 8 | 4 | Coarse time, echoed from the last packet DICE sent |
| 12 | 2 | Fine time, echoed back |
| 14 | 1 | Sensor state: 0 power-off, 2 booting, 3 configuring, 5 streaming, 6 resync, 7 retry |
| 15 | 1 | Settings status: 0 loaded, 1 defaults, 2 saving, negative failed |
| 16 | 4 | Frame generation, counts every image the sensor has produced |
| 20 | 2 | Result of the last sensor configuration, 0 is good |
| 22 | 2 | Result of the last shutter-policy check, 0 is good |
| 24 | 4 | Dose, signed, microrad |
| 28 | 4 | Dosimeter voltage, smoothed, microvolts |
| 32 | 4 | Dosimeter zero intercept, signed, microvolts |
| 36 | 4 | Dosimeter flags: 1 nominal calibration, 2 saturated, 4 stale, 8 zeroing |
| 40 | 4 | Supply voltage, millivolts |
| 44 | 2 | Raw converter mean, of 4095 |
| 46 | 2 | Raw converter standard deviation |
| 48 | 2 | Scene coldest pixel, centikelvin |
| 50 | 2 | Scene hottest pixel, centikelvin |
| 52 | 2 | Scene centre pixel, centikelvin |
| 54 | 2 | Encoded size of the image being sent; divide 38400 by it for the ratio |
| 56 | 4 | Time since the last shutter correction, milliseconds |
| 60 | 1 | Shutter mode: 0 manual, 1 auto, 2 external |
| 61 | 1 | Capture state: 0 idle, 1 correcting, 2 sending one image, 3 recording |
| 62 | 2 | Images sent in response to a single-image request |
| 64 | 112 | Twenty-eight 32-bit health counters, in the order below |
| 176 | 1072 | Zero padding |

The counters at offset 64, four bytes each, in this order: reset cause, fatal
code, clock failures, camera boot failures, sensor errors, forced corrections,
discarded sensor packets, sensor checksum errors, sensor sequence errors,
sensor resynchronisations, transfer retries, link stalls, transfer failures,
sensor bus errors, chunks processed, segments accepted, segments ignored,
frames completed, frames dropped, USB receive overruns, USB transmit busy,
converter overruns, RS-422 receive overruns, RS-422 checksum errors, RS-422
transmit busy, frames sent uncompressed, keyframes sent, longest compression
pass in microseconds, image chunks the transmitter asked for before the encoder
had produced them.

The order is `health_counters_t` in `include/health.h`; the block is written
straight from the struct, so appending a counter extends it and never moves an
existing one.

### The image payload

1280 bytes, of which at most 1264 are image. A compressed frame is typically
9 packets against the 31 an uncompressed one takes.

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | Frame generation, the same for every packet of one image |
| 4 | 2 | Chunk index, counting from 0 |
| 6 | 2 | Chunk count, or 0 when not yet known |
| 8 | 4 | Byte offset of this chunk within the encoded frame |
| 12 | 2 | Number of bytes in this chunk |
| 14 | 1 | Layout version, currently 2 |
| 15 | 1 | Codec mode, plus the end-of-frame flag |
| 16 | 1264 | Encoded image bytes |

| Mode | Meaning |
|---:|---|
| 0 | Raw pixels, uncompressed. The fallback; not normally seen |
| 1 | Keyframe, coded against itself |
| 2 | Difference against the previous frame |
| `+0x80` | Set on the last chunk of a frame |

**The chunk count is usually zero.** The camera starts transmitting before it
has finished compressing, so it does not yet know how many chunks the frame
will take. Collect chunks until one arrives with the `0x80` flag; that index
plus one is the count. A non-zero count can be trusted.

Version 1 put a 16-bit layout version at offset 14, so its byte 14 was always
zero and byte 15 was 1. That is how a decoder tells the two apart, and why
captures taken before compression still decode.

> **Raw image bytes are little endian**, unlike every other field in the
> protocol. That applies to mode 0 and to the decoder's output: each pixel is a
> little-endian 16-bit temperature in hundredths of a kelvin. The packet header
> around it is big endian.

## Host tools

All in `tools/`, all pure Python plus numpy, PySide6 and pyserial.

| Tool | Purpose |
|---|---|
| `thermalcam_app.py` | The main window. USB or RS-422, live temperature, capture, recording |
| `stp_monitor.py` | Ground-side RS-422 decoder: vitals, images, command injection |
| `frame_codec.py` | The image decoder. Import it if you are writing your own ground software |
| `thermalcam_cli.py` | Command-line control over USB CDC |
| `render_frame.py` | Turn a saved raw frame into a PNG |
| `rs422_diagnose.py` | Link diagnostics: listen, loopback, and a probe pattern |
| `generate_command_list.py` | Regenerates `COMMANDS.md` and checks every packet's CRC |
| `thermal_imaging.py` | Shared palettes, contrast curves and temperature conversion |

Two things bite when writing host software against this camera:

**Ask for a big receive buffer.** Decoding a frame takes tens of milliseconds
during which the port is not read, and the default driver buffer is too small
to cover the gap. The bytes lost to it show up as CRC errors and partial frames
that look like a bad link. Both tools call `set_buffer_size(rx_size=1 << 20)`.

**Only one process can hold each interface.** A stale window or monitor keeps
the port and silently swallows the traffic.

## Measured performance

On hardware, at 921600 baud, over 60 seconds of continuous streaming:

| Metric | Value |
|---|---|
| Delivered frame rate | 5.78 per second |
| Compression achieved | 3.57x |
| CRC errors, partial frames, checksum failures | 0, 0, 0 |
| Sensor capture rate | 8.8 per second, no resyncs |
| Worst encoder pass | 10.7 ms, against the 12.6 ms deadline |
| Uncompressed rate, for comparison | 1.85 per second |

**8.7 frames a second is not reachable at this baud.** It needs about 8 packets
a frame, so roughly 4.3x compression, and real scenes give 3.5x. In round
numbers: 8.7 frames of 9 packets is 100,850 bytes a second against 92,160
available.

The gap between 5.78 and the ~7.8 the link would allow is processor time, not
bandwidth. Compressing costs about 16 ms on a 100 MHz Cortex-M4 that is already
spending most of its budget assembling sensor packets, which holds the capture
rate below the sensor's 8.8. Closing it would mean driving transmission from
the DMA completion interrupt rather than the task loop.

## Budgets and constraints

| Resource | Used | Total |
|---|---:|---:|
| RAM | 240,800 | 262,144 |
| Flash | 43,328 | 1,048,576 |

RAM is the binding constraint, not flash. The large allocations are the two
frame buffers in the parser (76.8 kB), the codec reference frame (38.4 kB), the
two codec output slots (40.9 kB), the VoSPI DMA buffers (39.4 kB) and the
resync scan window (29.5 kB).

Things worth knowing before proposing a change:

- **On-chip video storage is not viable.** Free flash holds about 20 raw
  frames, or 2.3 seconds, and programming one takes ~154 ms against a 114 ms
  frame period. The part is single-bank, so program and erase stall the core.
  Buffering seconds of video in RAM is feasible; minutes needs an external QSPI
  part, which the board does not have.
- **921600 is the fastest baud available** on this bus. USART2 could reach
  3.125 Mbaud and the transceiver is rated far higher, but the other end is
  fixed.
- **Windows exposes only one UVC payload format.** Offering Y16 and YUY2
  together yields a YUY2-only device, so each build ships one
  (`UVC_ADVERTISE_SECOND_FORMAT`). `CAP_PROP_CONVERT_RGB=0` under DirectShow is
  the only path that returns raw 16-bit.

## Fault tolerance and flight readiness

The experiment flies in low Earth orbit and cannot be power cycled or touched.
Everything below follows from that: no failure may be permanent, and the only
way in is RS-422.

### It never speaks unless spoken to

`STP_BENCH_FREERUN` is 0 for flight. The camera sends nothing at power-up,
answers vitals only when asked, and streams images only when told. On a bus
shared with up to five experiments and the flight computer, anything else would
talk over somebody. The transceiver's driver enable is asserted only for the
duration of each packet and released in the transmit-complete callback.

Set it to 1 for bench work and the camera free-runs instead. **It must be 0 to
fly**, and it is checked by listening: a correctly configured camera returns
zero bytes to a passive listener.

### Nothing can stop it permanently

The independent watchdog runs from the LSI, outside the core clock and the
interrupt mask, so it resets the part even from a fault handler with interrupts
disabled. `board_fatal()` records the code, drops the bus and the sensor, then
waits for it. Verified by deliberately hanging the loop: the part went quiet
and came back seventeen seconds later reporting an IWDG reset in
`reset_cause`.

The timeout is deliberately generous. The only legitimate stall is a flash
sector erase, which the datasheet allows three seconds for, and that erase
refreshes the watchdog before it starts. A false reset in flight would be worse
than a slow recovery.

Failures of the dosimeter or of USB are recorded in `fatal_code` and otherwise
ignored, because neither is needed to fly. Only the RS-422 link is worth
refusing to run without.

### The sensor is supervised, not trusted

The Lepton can stop producing frames while the transport still looks perfectly
healthy: chunks keep arriving on time, but every one is discard packets. None
of the transport timeouts see that, and re-deriving the bit alignment is not an
escape from a sensor that has stopped. Observed on the bench, where it never
recovered.

Frames are therefore supervised directly. Five seconds without one triggers a
reacquisition; three of those escalate to cutting the sensor's power, which is
the only thing that revives a stopped Lepton. `camera_stalls` counts it. The
ladder was verified on hardware by faking the stall: resync, resync, resync,
power cycle, reboot, streaming.

### Every interface is checked

| Path | Protection |
|---|---|
| Stored settings | Magic, version and CRC32C; falls back to defaults if any fail |
| Sensor VoSPI | CRC on every 164-byte packet, verified, plus sequence checking |
| RS-422 | CRC-16/CCITT-FALSE on every packet, both directions |
| Image data | FNV-1a checksum of the source pixels, verified after decoding |

What is **not** implemented is triple modular redundancy, RAM scrubbing or ECC,
which the requirements list as optional. Corruption is detected at every
interface and recovered by retry or reset; it is not masked. One known gap:
`fatal_code` lives in `.bss` and does not survive the reset, so the ground sees
that the watchdog fired but not what caused it. Moving it to an RTC backup
register would close that.

## Testing

```powershell
.\.venv\Scripts\pio.exe test -e native
```

The native suite covers the CRCs, COBS framing, the wire and STP packet
formats, VoSPI segment assembly, and the image codec: round-trips for both
predictors, extreme pixel values, truncated and corrupted streams, and the
refusal to decode a difference frame without its reference.

It needs a host C compiler on `PATH`; PlatformIO's native platform expects
`gcc`:

```powershell
winget install --id BrechtSanders.WinLibs.POSIX.UCRT --exact
```

The codec is also cross-validated end to end: the C encoder's output is decoded
by the Python decoder and compared bit-for-bit against 50 real frames. On
hardware, every frame's checksum is verified by the ground tools, so a
regression in either implementation surfaces as a reported failure rather than
a subtly wrong image.

## Flashing and debugging

SWD over an FT2232H. See [FT2232 Information.md](FT2232%20Information.md) for
adapter wiring and driver setup.

```powershell
& "$env:LOCALAPPDATA\Microsoft\WinGet\Packages\xpack-dev-tools.openocd-xpack_Microsoft.Winget.Source_8wekyb3d8bbwe\xpack-openocd-0.12.0-7\bin\openocd.exe" `
  -f debug\cjmcu-ft2232h-swd.cfg -f target\stm32f4x.cfg `
  -c "program .pio/build/target/firmware.elf verify reset exit"
```

Do not change the SWD driver configuration while debugging capture timing; the
CJMCU adapter is the one known to work reliably here. Note that halting the
core stops the camera: readings taken while halted are not evidence about a
running system.

The development USB VID/PID is `1209:F412`; a production allocation is still
required.
