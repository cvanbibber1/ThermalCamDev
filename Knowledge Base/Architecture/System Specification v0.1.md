# Thermal camera system specification v0.2

## 1. Purpose and status

This is the review-first specification for an STM32F412CGU6 camera controller using a
FLIR Lepton 3.1R, USB Full-Speed, an analog dosimeter input, FT2232H SWD, and an
ADM2582E multidrop serial link. RS-485 firmware is deliberately the final implementation
phase, but its complete wire protocol is defined now.

Firmware implementation is authorized. Multidrop electrical connection remains blocked
until the ADM2582E DE pull-up is removed and the physical bus topology is confirmed.

## 2. Functional requirements

The final firmware shall:

1. Boot reliably from internal flash and remain recoverable through SWD and NRST.
2. Power, reset, configure, and monitor the Lepton 3.1R.
3. Acquire radiometric 160 x 120 frames without losing VoSPI synchronization.
4. Expose thermal video as a USB Video Class stream.
5. Expose camera controls, diagnostics, dosimeter telemetry, and firmware information
   over a USB command channel.
6. Sample the dosimeter on PA4 and publish calibrated and raw low-rate telemetry.
7. Later expose the same command model and frame data over a collision-free addressed
   multidrop differential bus.
8. Continue acquiring frames when an output transport stalls; transports may drop old
   frames but must not block the Lepton capture pipeline.

## 3. Non-functional requirements

- No dynamic allocation after initialization.
- All external byte streams use bounded parsing, explicit lengths, versioning, and CRCs.
- Watchdog recovery shall not leave the ADM2582E driver enabled.
- A failed Lepton command or lost VoSPI synchronization must recover without MCU reset.
- Configuration changes that alter video format shall pause publication, resynchronize
  VoSPI, and resume with a new stream epoch.
- Persistent settings shall be versioned and CRC-protected in MCU flash. Do not write
  Lepton OTP during normal operation.

## 4. Hardware architecture

See [[../Hardware/Pin Map]] for the canonical pin table.

### 4.1 Clock tree

The MAX7375AXR805 on PH0 supplies the STM32's 8 MHz HSE. The MCU clock tree targets
100 MHz SYSCLK and 48 MHz USB from PLLI2SQ. The Lepton master clock is a separate
always-on source and is not generated by the MCU. USB VBUS sensing is disabled because
the connector carries data only.

### 4.2 Memory budget

Minimum static allocation target:

| Use | Approximate bytes |
|---|---:|
| Two 160 x 120 x 16-bit frame buffers | 76,800 |
| One 60-packet Raw14 VoSPI segment buffer | 9,840 |
| USB UVC payload/FIFO staging | 4,096 to 8,192 |
| RS-485 RX/TX queues and framing | 4,096 to 12,288 |
| Protocol state, stacks, diagnostics | Budget from remaining SRAM |

The 256 KiB SRAM is sufficient if buffers are static and ownership is explicit.

## 5. Boot and camera bring-up

1. Start with `RS485_DE=0`, Lepton `CS_L=1`, `RESET_L=0`, and `PWR_DWN_L=0` using
   hardware pulls that are safe before firmware configures GPIO.
2. Start and validate HSE, main PLL, PLLI2S, and the USB clock. The separate 25 MHz
   Lepton clock has no MCU measurement connection and is validated with test equipment.
3. Drive `PWR_DWN_L=1` while keeping `RESET_L=0`.
4. After rails and clock are stable, drive `RESET_L=1`.
5. Wait at least 950 ms before CCI access. Because the 3.1R has a shutter, use a 5 s
   initial deadline and poll the boot-status bit rather than assuming a fixed completion.
6. Read CCI status, verify boot status and non-busy state, then read part number,
   serial number, and software revision.
7. Configure TLinear radiometry, Raw14 output, desired telemetry mode, and GPIO3 VSYNC.
8. Establish VoSPI synchronization and publish health before enabling external streaming.

Any failure enters a bounded retry state with a diagnostic counter. After repeated CCI
failure, perform a camera-only reset and restart this sequence.

## 6. Runtime architecture

The firmware is divided into services with single ownership:

- **Camera control service** owns Lepton CCI and serializes all commands.
- **Frame acquisition service** owns SPI2 DMA, VSYNC, VoSPI parsing, CRC checking,
  resynchronization, and frame buffers.
- **Frame broker** publishes immutable complete-frame references to USB and RS-485.
- **USB service** owns UVC and the USB command endpoint.
- **Dosimeter service** owns ADC acquisition, filtering, calibration, and telemetry.
- **Field-bus service** owns USART2, DE timing, addressing, framing, and bus scheduling.
- **Health service** owns watchdog votes, counters, reset causes, and status snapshots.

ISR work must be limited to timestamping, clearing hardware state, and queueing bounded
events. Parsing and camera commands run outside interrupts.

## 7. Shared command model

USB and RS-485 shall terminate in one command dispatcher. Every request contains:

- protocol version;
- request ID/sequence;
- operation code;
- target resource;
- bounded payload length;
- caller transport and authorization level.

Required command families:

- Device information, health, reset cause, and firmware version.
- Lepton status, part/serial/software information, and FFC status.
- Lepton AGC, SYS, VID, OEM, and RAD get/set/run operations supported by the 3.1R.
- Explicit FFC run.
- Raw CCI register access in maintenance mode.
- Stream configuration, start/stop, single-frame snapshot, and statistics.
- Dosimeter raw ADC, filtered voltage, calibration, and telemetry rate.
- Persistent node address and bus configuration.
- Bootloader/reboot request with an explicit confirmation token.

Commands are serialized against video-format changes. Read-only commands may run while
streaming. A command that changes packet size, radiometry mode, telemetry placement, or
video format creates a new stream epoch and forces VoSPI resynchronization.

## 8. Observability and fault handling

Maintain saturating or 64-bit counters for:

- camera resets and boot failures;
- CCI NACK, busy timeout, and command error codes;
- VoSPI discard packets, invalid segments, sequence errors, CRC errors, and resyncs;
- complete, duplicate/invalid, and dropped frames;
- USB queue overruns and host stalls;
- ADC overruns and calibration status;
- RS-485 framing, CRC, address, collision/timeout, and queue errors;
- watchdog and brownout reset causes.

Status snapshots shall be readable over both command transports and optionally emitted at
one low-rate telemetry interval.

## 9. Implementation sequence

1. Validate SWD, MCU clocks, USB enumeration, and safe reset output states.
2. Create STM32Cube project, clock test, SWD recovery, and diagnostic logging.
3. Implement USB command transport and device health.
4. Implement Lepton power/CCI driver and camera self-identification.
5. Implement VoSPI DMA capture and frame validation.
6. Implement USB UVC publication.
7. Implement dosimeter acquisition and telemetry.
8. Implement and qualify the ADM2582E multidrop transport last.
